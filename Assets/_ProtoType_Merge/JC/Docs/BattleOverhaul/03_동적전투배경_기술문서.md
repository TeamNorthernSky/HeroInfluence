# 동적 전투 배경 구성 기술문서

확인일: 2026-10-13 · JC_Testbed 작업 트리 기준 · [문서 안내](README.md)

## 목적과 보장 범위

아놀드는 이동하므로 고정 이벤트마다 배경을 미리 만드는 방식만으로 대응할 수 없습니다. 현재 구현은 실제 조우 시점의 탐사 외형을 읽고, 근처에서 진형을 펼칠 수 있는 공간을 찾아 전투용 좌표계로 옮깁니다. 아놀드의 장소를 세 개 또는 열 개의 미리 만든 배경 중에서 고르는 구조가 아닙니다.

다만 **동적 구성은 모든 좌표에서 반드시 생성에 성공한다는 뜻은 아닙니다.** 도로로 판독되는 공간, 진형 크기, 장애물, 시야, 탐색 반경과 최대 확대율의 제약이 있습니다. 실패하면 기존 전투 배경과 공통 카메라·UI를 사용합니다. 현재 지원되는 1구역 맵 구조에서 기본 기능을 확보한 상태이며, 다른 지역·새 메시 형식까지 자동 지원한다고 가정하면 안 됩니다.

## 세 좌표를 구분하기

| 이름 | 의미 | 사용처 |
|---|---|---|
| 실제 조우 위치 | 전투 진입 직전 플레이어 파티의 탐사 월드 위치 | 후보 탐색의 원점, 생성 기록 |
| 배경 기준점 | 공간·시야 검사를 통과한 최종 탐사 월드 위치 | 탐사 외형의 이동·회전·확대 기준 |
| 전투 진형 좌표 | 전투씬의 PlayerPlace·EnemyPlace 및 셀 배치 | 전투 캐릭터와 타겟 선택 |

배경 기준점은 조우 위치와 달라질 수 있습니다. 탐사 파티를 그 기준점으로 이동시키는 것이 아니라 배경을 가져오는 기준을 바꾸므로, 전투 종료 후 파티가 주차장으로 이동하는 기능은 아닙니다. 탐사 타일의 이동 판정과 전투 셀 배열도 동일한 구조가 아닙니다.

## 진입부터 표시까지

```text
DH 적 턴: 파티와 적의 인접 여부 확인
  → 직접 전투 또는 이벤트 대화 후 전투 컨텍스트 설정
  → CombatStarted(party, enemy 또는 null)
  → CombatSceneEntryController
  → JcArnoldBattlePresentation.Prepare
      조우 입력 확정 → 탐사 외형 Capture → 후보 Resolve → 배경 Build
  → 탐사씬 전환 중 DDOL 소유자가 생성 결과 보관
  → 전투씬 로드
      생성 결과 이동·활성화 → 기존 배경 Renderer 숨김 → 카메라·UI 적용
  → 전투씬 종료 시 생성 자원 해제
```

`EnemyTurnController.TryBeginCombat`는 파티와 적의 그리드 좌표로 인접 여부를 판단합니다. 그러나 JC 배경 생성에 직접 전달하는 값은 `GetCurrentGrid()` 값이 아니라 **해당 시점 객체의 Transform 월드 위치**입니다. 이동 좌표계와 시각 좌표계가 바뀌면 이 연결부도 확인해야 합니다.

이벤트 경로는 `DHEventBattleRuntimeManager`가 전투 컨텍스트를 만들고 적 인수를 `null`로 보낼 수 있습니다. 이때 `SourceEnemyPlacementKey`와 `EnemyIdentity.PlacementKey`를 대조해 원래 적을 찾습니다. 이 키는 위치 좌표가 아니라 객체 식별자입니다.

DH의 기존 적 이동·인접 판정·전투 컨텍스트와 JC가 추가한 배경 생성 연결이 함께 작동합니다. 기존 DH 파일에도 JC 연결 변경이 있으므로 폴더 소속만으로 수정 책임을 단정하지 않습니다. 씬 진입 연결인 `CombatSceneEntryController` 자체는 JC 폴더에 있습니다.

## 입력 결정: 아놀드와 고정 이벤트

`ResolveBackgroundSettings`의 이동형 적 분기는 파티 위치를 `encounterPosition`, 적 위치를 `enemyPosition`으로 넣습니다. 아놀드는 이 경로를 사용하며 이벤트별 고정 기준점 프로필을 읽지 않습니다. 두 위치의 중간점을 조우 원점으로 사용하지도 않습니다.

고정 이벤트는 `SetFixedOrigin`으로 받은 객체, `SourceMainEventKey`와 구역에 해당하는 이벤트 객체, 적 객체 등의 입력으로 기준을 찾습니다. 필요하면 `JcBattlePresentationProfile.Find(zone, key)`의 이벤트별 기준점·축 예외를 적용합니다. 이는 아놀드의 동적 후보 선정과 별개의 기능입니다.

현재 `UsesExplorationBackground`는 이벤트 전투 또는 Field 타입에 배경 생성을 허용합니다. **점령전은 기존 배경만 사용한다는 기획을 명시적으로 분리하는 조건은 충분하지 않습니다.** 은행·본부에서 고정 위치 입력을 찾지 못해 기존 배경으로 복귀하는 것은 정상 분류와 다릅니다. 향후 이 조건을 보완할 때 실제 대화 선택지가 생성한 전투 컨텍스트를 기준으로 분류해야 합니다.

## Capture: 무엇을 가져오는가

허용되는 탐사 루트는 다음과 같습니다.

```text
Land / DecorativeSystemAndRoot / JC_WorldDressing
GateSystemAndRoot / HeroUnionSystem / OutpostSystemAndRoot
VillainUnionSystem / ObstacleRoot
```

활성 `MeshFilter`와 사용 가능한 `MeshRenderer`를 읽습니다. 비활성 객체, 꺼진 Renderer, `forceRenderingOff` 상태, 메시가 없는 객체는 제외합니다. 캐릭터 관련 부모와 Armature 계열, 이미 생성된 동적 배경도 제외합니다. 따라서 원본 지형을 숨기고 JC 월드 드레싱 외형을 표시했다면 **보이는 대체 외형**이 입력에 들어갑니다.

각 부분에는 메시, 원본 메시 식별자, 재질, 월드 행렬, Bounds, 지형 여부 및 실행 중 Renderer 참조가 저장됩니다. 이는 GameObject 전체 복제가 아닙니다. 스크립트·Collider·이벤트·이동 규칙을 전투 배경으로 복제하지 않습니다. SkinnedMeshRenderer, 파티클, 라이트도 현재 일반 캡처 대상으로 보장되지 않습니다.

지형 여부는 `Generated Tile Meshes` 또는 `JC_ExploreDetail_Visuals` 계층 등을 통해 판정합니다. 도로 후보 정보는 원래 `TileChunk_`와 `Road_` 계열 텍스처에서 별도로 읽습니다. 도로 원본 Renderer가 드레싱 때문에 숨겨져도 도로 후보 정보는 필요하기 때문입니다.

**도로 정보는 주차장과 일반 차도를 세밀하게 의미 분류하지 않습니다.** 주차장이 해당 도로 외형으로 구성되어 있고 충분한 공간이 있으면 전투 후보가 됩니다. `ParkRoad`는 흙길 계열 이름이므로 주차장이라는 뜻으로 해석하면 안 됩니다.

## Resolve: 근처의 어느 공간을 선택하는가

다음 값은 코드 초기값이며 사용자 프로필에서 바뀔 수 있습니다.

| 설정 | 초기값 | 의미 |
|---|---:|---|
| `anchorSearchRadius` | 8 | 탐사 좌표계에서 주변 기준점을 찾는 거리 |
| `captureRadius` | 18 | 선택 기준점 주변 외형을 수집하는 범위 |
| `scale` | 3 | 첫 균일 확대율 |
| `maxAutoScale` | 8 | 자동 확대의 상한 |
| `battleWidth` | 11.5 | 필요한 전투 가로 범위 |
| `battleLength` | 36 | 필요한 전투 세로 범위 |

후보는 요청 위치, 반경 내 도로 중심, 도로 중심에서 반 셀만큼 이동한 위치들입니다. 후보마다 X·Z 방향과 0.25 단위 확대율을 검사합니다. 전투 폭·길이에 여유를 더한 직사각형을 탐사 좌표계로 역산한 뒤, 약 0.2 간격으로 표본을 찍어 같은 높이의 도로가 모두 받쳐 주는지 확인합니다.

이어 비지형 Bounds와 진형 공간의 겹침, F6/F7 시점에서 여러 진형 표본점을 향한 시야를 검사합니다. 시야 검사는 렌더링 결과가 아니라 Bounds 기반의 보수적인 근사입니다. 모든 캐릭터·모든 임의 카메라의 완전한 가시성을 보장하지 않습니다.

통과한 후보의 점수는 대략 다음과 같습니다.

```text
점수 = 조우 원점부터의 거리
     + (후보 확대율 - 시작 확대율) × 1.5
     + 접근 방향 불일치에 대한 매우 작은 보정
```

가장 낮은 점수의 후보를 선택합니다. **원래 위치가 가능하면 무조건 그 위치를 먼저 확정하는 알고리즘이 아닙니다.** 가까워도 큰 확대가 필요한 좁은 도로보다, 조금 떨어져 있어도 작은 확대만 필요한 넓은 주차장이 유리할 수 있습니다.

사용자가 보고한 “도로에서 아놀드를 만났지만 옆 주차장에서 전투”는 이 규칙으로 설명 가능한 결과입니다. 다만 해당 배포 실행의 정확한 입력 좌표와 생성 로그가 없으므로 그 한 건의 점수까지 재현했다고 볼 수는 없습니다. 장소 일치감을 강화하려면 향후 도로 유형 분류, 원점 우선 정책, 이동 비용 등을 별도 조정해야 합니다.

후보가 없으면 예외를 발생시키고 기존 배경으로 복귀합니다. 공간을 만들기 위해 건물을 밀거나 탐사 도로 폭을 수정하지 않습니다. 남아 있는 legacy clearance 필드를 장애물 이동 기능으로 해석하지 마세요.

## Build: 좌표 변환과 원형 보존

선택한 탐사 기준점을 `p`, 방향 회전을 `R`, 균일 확대율을 `s`라고 하면 다음 변환을 적용합니다.

```text
전투 좌표 = R × s × (탐사 월드 좌표 - p)
X 방향 선택: Y축 -90도 회전 / Z 방향 선택: 기준 회전
```

진형은 전투씬의 좌표를 유지하고 배경이 그 주위로 배치됩니다. X축만 늘리는 식의 도로 변형 대신 **전체 외형을 균일 확대**하므로 도로와 건물의 원래 관계를 보존합니다. 그 결과 근거리 디테일 부족이 더 잘 드러날 수 있어 월드 드레싱과 전투 표면 보강이 추가되었습니다.

선택 범위 안의 지형은 출력 범위로 잘라 메시를 만들고, 비지형은 변환하여 복사합니다. 노멀은 행렬에 맞게 변환합니다. 출력 루트는 `JC_DynamicEncounter`이며 씬 저장용 원본이 아닌 임시 결과입니다.

생성 기록에는 `조우 → 기준점 / 이동 / 방향 / 동일 확대 / 원형 보존 외형 수`가 남습니다. 문제 제보에는 전투 화면뿐 아니라 이 기록을 함께 확보하면 후보 선정 문제와 외형 누락 문제를 구분할 수 있습니다.

## 전투 전용 표면 보강

배경 생성 후 `JcBattleSurfaceDressing.Apply`가 실행됩니다. 도로의 기존 표식·UV 방향을 바탕으로 전투 크기에 맞는 중앙 점선을 다시 표현하고 횡단보도를 흰색과 약한 요철로 처리합니다. 모든 평평한 아스팔트에 무조건 차선을 긋지 않으므로 주차장은 주차장 형태를 유지합니다.

야지 소품은 잔디 텍스처와 위를 향한 삼각형을 판독해 면적 가중 표본을 뽑습니다. 별도의 `System.Random`과 조우 좌표 기반 seed를 사용하며 전역 Unity 랜덤 상태를 소비하지 않습니다. 배치 제한에는 진형 보호 범위, 간격, 지지면 높이, 장애물, 카메라 시야가 포함됩니다. 소품 수가 0인 결과도 정상일 수 있습니다.

현재 기본 프로필의 점선 폭·길이·간격은 0.15 / 2.5 / 3.5이고 소품 상한은 28입니다. 이는 게임 월드 단위의 표시 기준이며 실제 도로 법규를 완전히 재현한다는 의미는 아닙니다. `Tree`로 시작하는 이름으로 수목 크기를 구분하는 현재 방식은 새 소품 종류가 늘어날 때 명시적 분류로 바꾸는 편이 안전합니다.

## 자원 수명과 빌드 입력 캐시

씬 전환 중에는 `JC_BattlePresentation` 소유자가 결과를 보관합니다. 목표 씬 로드 이후 해당 씬으로 옮기며, 전환 대기에는 타임아웃이 있습니다. 전투씬 종료 시 `JcDynamicBattleOutput`이 소유한 메시·복제 재질·임시 텍스처를 정리합니다.

MaterialPropertyBlock은 선언된 셰이더의 색·벡터·수치·텍스처를 복제 재질에 옮깁니다. 모든 종류의 렌더러 상태를 복사하는 범용 프리팹 복제는 아닙니다. 레이어, 그림자 옵션, 라이트맵, LOD 등은 별도 검토가 필요합니다. 영구 에셋 텍스처는 공유하고 임시 Texture2D·RenderTexture는 별도로 보존합니다. 지원하지 않는 임시 텍스처 타입은 실패할 수 있습니다.

현재 물 재질은 출력에서 `_FollowCanal`을 0으로 바꿉니다. 탐사 월드 좌표용 흐름 지도를 배경의 이동·회전·확대에 맞춰 재매핑하지 않았기 때문입니다. 전투에서도 물 셰이더는 사용할 수 있지만, 원래 수로 굴곡을 따라가는 방향 지도까지 동일하게 전달되는 것은 아닙니다.

빌드에서는 CPU로 읽을 수 없는 원본 메시가 있을 수 있습니다. 이를 위해 Editor 메뉴 **`JC/전투 테스트/동적 배경 공통 입력 수집`**이 `Resources/JC_Encounters/DynamicSource`와 관련 메시·재질 에셋을 준비합니다. 실제 캡처에서 읽기 불가능한 메시를 만나면 원본 메시 참조와 캐시를 대조합니다. 대응 자원이 없으면 생성 실패 후 기존 배경으로 복귀할 수 있습니다.

이 캐시는 **전체 맵의 읽기 가능한 외형 입력**입니다. 주차장 등 전투 위치를 사전에 정한 프리셋이 아닙니다. 에디터에서는 성공하지만 빌드에서 실패할 경우 캐시와 새 원본 메시의 대응을 먼저 확인하세요. 지형이나 프리팹 메시를 바꾼 뒤에는 캐시를 다시 만들고 실제 빌드를 검증해야 합니다.

2026-10-13 베이크 도구 전환 이후 탐사 드레싱은 확정 에셋에서 가져옵니다. 공통 입력 수집은 탐사 드레싱을 자동 재생성하지 않습니다. 새 외형을 반영하려면 드레싱 재생성·확정 후 공통 입력을 수집합니다. 미리보기가 활성 상태이면 먼저 확정하거나 취소해야 합니다.

수집 메뉴는 편집 모드에서 사용합니다. 이미 열린 원본 씬에 미저장 변경이 있으면 중단하는 보호가 있습니다. 수집을 위해 미저장 사용자 작업을 버리거나 임의 저장하지 마세요. 메뉴가 생성하는 에셋과 실제 사용자 씬 저장은 구분합니다.

시험용 `Arnold_Dynamic` 적 편성 프리셋, 과거 Main_1-1·1-2·2-2의 고정 배경, 실전 아놀드 조우 입력, 위 전체 맵 캐시는 목적이 다릅니다. 이름에 preset이 있다는 것만으로 실전 위치가 고정되었다고 판단하지 않습니다.

## 데코레이션 확장의 현재 기반과 후속 설계

현재는 두 경로가 있습니다. 탐사씬의 허용 루트 아래에 있는 일반 MeshRenderer 소품은 실제 배치 상태로 캡처할 수 있습니다. 전투 전용 잔디 소품은 캡처 이후 별도로 생성합니다. JC 월드 드레싱이 만든 결과도 첫 번째 경로에 포함됩니다.

향후 가로수·벤치·표지판 등을 추가할 때에는 다음 순서를 권장합니다. 아래는 **후속 설계안이며 이번에 구현된 기능은 아닙니다.**

1. 탐사 배치 데이터와 렌더링 결과를 분리하고, `JC_WorldDressing` 하위 생성물에 안정된 식별자를 부여합니다.
2. 전투 포함 여부, 진형 장애물 여부, 작은 소품 여부를 이름 대신 명시적 메타데이터로 관리합니다.
3. 나무의 잎 전체 Bounds가 후보를 과도하게 배제하지 않도록 줄기·시야·장식 범위를 구분합니다.
4. LOD·인스턴싱·MaterialPropertyBlock·레이어·그림자 옵션의 전달 범위를 정합니다. 파티클과 SkinnedMesh는 별도 어댑터가 필요합니다.
5. 읽기 가능한 메시 캐시를 갱신하고 Editor와 배포 실행을 함께 확인합니다.
6. 기존 소품 캡처와 전투 전용 랜덤 배치가 같은 위치에 중복되지 않는지 확인합니다.

후보 선정과 외형 복사는 책임이 다릅니다. 소품이 보이지 않는 문제를 해결하려고 공간 탐색 조건부터 완화하지 말고, 먼저 허용 루트·렌더러 형식·활성 상태·범위·캐시를 확인하세요.

## 수정 후 최소 확인

좁은 도로, 교차로, 주차장 인근, 산 경계, 수로·다리 인근을 포함해 확인합니다. 같은 위치 반복 시 선택 결과, 기존 배경으로 복귀하는 이유, 종료 후 탐사 파티 위치와 자원 해제를 기록합니다. 상세 절차와 과거 검증의 한계는 [검증과 인수인계](05_검증과인수인계.md)를 따릅니다.

| 증상 | 먼저 볼 지점 |
|---|---|
| 가까운 다른 장소가 선택됨 | 요청 위치와 최종 기준점, 거리·확대율 점수, 도로 판독과 Bounds 검사 |
| 기존 배경만 표시됨 | `[JC Battle]` 경고, 이벤트 기준 객체, 도로 후보 유무, 읽기 가능한 메시 캐시 |
| 소품 일부 누락 | 루트 허용 목록, MeshRenderer 여부, 활성·forceRenderingOff, 캡처 반경 |
| 기존 건물이 새 배경과 겹침 | 기존 배경 숨김의 루트 이름 규칙: Ground·HeroUnionZ1·BGOffice·BGHouse·BGStore |
| 물 방향이 탐사와 다름 | 출력의 `_FollowCanal=0` 및 원래 흐름 지도의 좌표계 |
| 반복 전투 뒤 메모리 증가 | 출력 소유 자원 목록, 씬 전환 소유자, RenderTexture 해제 |
