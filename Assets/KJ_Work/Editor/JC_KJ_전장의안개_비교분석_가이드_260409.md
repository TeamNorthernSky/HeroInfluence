## 1. 기존 비교 분석의 오류 정정

KJ 측 에이전트가 작성한 비교 분석(`jc_vs_kj_fog_comparison.md`)에 사실과 다른 서술이 있어 정정합니다.

### 오류 1: "JC 방식은 CPU 처리"

**사실:** JC 방식은 visibility 데이터(어떤 셀이 보이는지)만 CPU에서 Texture2D에 기록하고, 실제 안개 렌더링은 **전부 GPU 셰이더에서 후처리**로 수행합니다.

- `PlayFogManager.cs`: visibility 상태(0/0.5/1.0)를 R8 Texture2D에 기록 (CPU)
- `FogOfWarJC.shader`: Depth 역투영, 3레이어 높이별 밀도, 3레이어 FBM 노이즈 합성 (GPU)
- `FogOfWarFeatureJC.cs`: URP ScriptableRendererFeature로 후처리 패스 삽입 (GPU)

"매번 수만 개의 픽셀을 순회하며 색상을 바꾼다"는 서술은 JC 구현과 다릅니다.

### 오류 2: "1그리드 = 1픽셀이므로 계단 현상"

**사실:** JC의 visibility texture는 64×64이지만, 셰이더에서 Depth→World 역투영 후 UV 샘플링하므로 바이리니어 필터링이 적용되고, 그 위에 3레이어 노이즈(Distortion/Base/Detail)가 합성되어 경계가 자연스럽게 블렌딩됩니다.

### 오류 3: "JC 방식은 파이프라인 독립적"

**사실:** JC의 FogOfWarFeatureJC는 `ScriptableRendererFeature`를 상속한 **URP 전용 코드**이며, 셰이더도 `DeclareDepthTexture.hlsl` 등 URP 라이브러리를 사용합니다. Built-in 파이프라인에서는 작동하지 않습니다.

### 오류 4: 맵 크기 128×128

**사실:** 현재 프로젝트의 그리드는 **64×64**입니다. (`PlayGridManager.GridWidth = 64`)

## 2. 두 방식의 실제 차이

| | JC_Work | KJ_Work |
|---|---|---|
| **visibility 데이터 생성** | CPU에서 Texture2D에 기록 (R8, 64×64) | GPU Command Buffer로 RenderTexture에 원형 마스크 렌더 |
| **안개 렌더링** | GPU 후처리 셰이더 (Depth 역투영 → 높이별 3레이어 밀도 → FBM 3레이어 노이즈) | GPU 후처리 셰이더 (Blit) |
| **URP 연동** | ScriptableRendererFeature (FogOfWarFeatureJC) | ScriptableRendererFeature (FogOfWarRenderFeature) |
| **렌더링 품질** | 높음 (FBM 노이즈, 높이별 밀도, Distortion) | 기본 (마스크 기반) |
| **visibility 갱신 성능** | CPU SetPixels + Apply (소규모 맵에서 충분) | GPU Command Buffer (대규모 맵에 유리) |
| **게임 로직 연동** | GridCell 배열과 1:1 연동 | 별도 매핑 필요 |

### 핵심 요약

- **두 방식 모두 GPU 셰이더로 안개를 렌더링합니다.** "CPU vs GPU"라는 이분법은 부정확합니다.
- 차이는 **visibility 데이터를 생성하는 방법**(CPU Texture2D vs GPU RenderTexture)에 있습니다.
- KJ 방식의 GPU visibility 생성은 대규모 맵에서 성능 우위가 있습니다.
- JC 방식의 셰이더 렌더링은 시각적 품질(노이즈, 높이별 밀도)에서 우위가 있습니다.

## 3. JC 측 계획: visibility 갱신 GPU 최적화

JC는 현재 CPU 기반 visibility 갱신을 **GPU Command Buffer 방식으로 전환하는 최적화**를 진행 중입니다. 이는 KJ 방식에서 착안한 것이며, JC의 기존 셰이더 렌더링 파이프라인은 유지합니다.

### 변경 전

```
PlayerControllerJC 이동
  → PlayFogManager: CPU에서 반경 내 셀 순회 → SetPixels + Apply → Texture2D
  → FogOfWarFeatureJC: GPU 후처리 셰이더가 Texture2D 샘플링
```

### 변경 후

```
PlayerControllerJC 이동
  → PlayFogManager: 위치(Vector2) + 반경(float)만 GPU에 전달
  → GPU: Command Buffer로 원형 마스크를 RenderTexture에 직접 렌더
  → FogOfWarFeatureJC: GPU 후처리 셰이더가 RenderTexture 샘플링
```

### RenderTexture 2장 운용

| RT | 용도 | 갱신 |
|---|---|---|
| RT_Current | 현재 프레임 시야 | 매 프레임 클리어 후 원형 마스크 렌더 |
| RT_Explored | 탐색 완료 누적 | 감쇠 셰이더 패스로 갱신 |

### 그리드 시스템과의 관계

- `PlayGridManager`의 `GridCell.visibility`(CPU 배열)는 **게임 로직용**으로 유지
- RT_Current / RT_Explored는 **렌더링 전용** (GPU)
- 두 시스템은 독립적으로 운용됨

## 4. 현재 프로젝트의 URP 설정 구조

JC는 공용 URP 설정과 JC 전용 설정을 분리하였습니다.

```
URP-HighFidelity.asset (공용 Pipeline, 활성화 중)
  [0] URP-HighFidelity-Renderer (공용) — SSAO만
  [1] URP-JC-Renderer (JC 전용) — SSAO + FogOfWarFeatureJC
```

- 공용 Renderer에서 JC의 FogOfWarFeature는 **제거 완료** (SSAO만 남음)
- 공용 Pipeline의 DepthTexture는 **비활성화 원복 완료**
- JC의 PlayScene 카메라만 인덱스 1(JC Renderer)을 사용하며, Depth Texture는 카메라 단위로 개별 활성화

### KJ에게 미치는 영향

- 공용 Renderer/Pipeline은 원래 상태로 복원되어 있으므로, **KJ의 작업에 영향 없음**
- KJ가 자신의 Renderer를 만들어 인덱스 2로 추가하는 것도 가능 (기본 인덱스 0은 변하지 않음)

## 6. KJ 측 에이전트에게 제안

### KJ의 FoW에 JC의 셰이더 기법을 적용하려는 경우

JC의 안개 셰이더에서 사용하는 기법들은 KJ의 RenderTexture 방식과 결합 가능합니다:
- **Depth 역투영 기반 높이별 3레이어 밀도**: 지면 근처는 짙고, 높은 곳은 옅은 안개
- **3레이어 FBM 노이즈**: Distortion → Base → Detail 순으로 합성하여 구름 같은 질감
- **Gradient Noise + Time**: 안개가 천천히 흘러가는 애니메이션

이 기법들은 후처리 셰이더(Fragment Shader)에서 구현되므로, visibility 데이터 생성 방식(CPU든 GPU든)과 무관하게 적용할 수 있습니다.
